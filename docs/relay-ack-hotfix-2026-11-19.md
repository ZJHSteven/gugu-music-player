# 2026-11-19 公网音频中继 2 MiB ACK 阻塞热修复

## 真实反馈和现场证据

在真实 Owlbear 多房间交叉测试中，多位独立玩家能够看到正在播放的曲目，但多数无法听到音乐；已经有一台设备能成功接收并播放另一房间的曲目，因此不能简单归因于所有用户的浏览器都禁止自动播放。

从源端 GM 的实际浏览器运行时观察到：

- 当前曲目文件约 **2,188,046 B**，GM 本地 SHA-256 校验正确；
- 正式 Cloudflare DO WebSocket 已连接，源端收到两个不同远端 peer 的 `serve` 请求；
- 对两个 peer 都发送了**前 8 个 256 KiB** 二进制块；
- 原逻辑在第 8 块进入 `waitForAck(index=7)`，当时均未收到接收方 ACK；
- 旧版发送端因此不能继续发送超出第一个 2 MiB 窗口的尾部文件内容。此现象非常符合玩家一直无法完成文件下载的反馈，但无法从服务端直接确定客户端为何没有 ACK。

Cloudflare 实时尾日志可确认来自独立设备的 `/relay` WebSocket 接入；但生产版没有输出每一帧的 ACK/下载进度遥测，不能据此臆断接收端的浏览器具体报错。**仍需远端客户端刷新后实际验证是否能出声。**

## 仅修复发送端、不混入尚未验证的功能

此热修复从已上线的 `30580b4` 生产版本单独创建 `hotfix/relay-ack-prod` 分支。保留原始 Owlbear 房间元数据格式、现有播放器时钟算法、已有 OPFS/IndexedDB 以及 Cloudflare DO 中继协议，不合并开发分支的双 GM 时钟与 ZIP 备份等改动。

新增 `public/cloud/audio-sender.js`：按 256 KiB 切片发送，`WebSocket.bufferedAmount` 限制本地缓冲队列最多约 2 MiB，8 块之间让出事件循环，**不再将自定义 ACK 当作必须收到的下一批发送许可**。保留兼容已有接收端的 ACK 消息，仍然只在接收端凑齐完整文件、文件大小匹配且 SHA-256 相同时保存到本地缓存；断线不冒充传输成功。

## 自动化与真实中继验收

- 云版 **13/13**，原版 Node **42/42**，原版 Edge 浏览器 UI **61/61**。
- 单元专项：比 2 MiB 窗口多两块的完整二进制传输，即使接收端完全没有 ACK，重组 SHA-256 仍一致；中途断线不能返回成功。
- 真实 **本地 DO WebSocket**：随机隔离房间，两个独立客户端，无 ACK 完整接收 **3,145,745 B**，SHA-256 一致。
- 真实 **生产 Cloudflare DO WebSocket**：同样的隔离房间条件，直接连接 `wss://music.zjhstudio.com/relay`，无 ACK 完整接收 **3,145,745 B**，耗时 **2,886 ms**，SHA-256 一致。
- 线上 HTTP 校验：`/manifest.json` 已为 **v3.2.2**，`/cloud/audio-sender.js` 和 `/cloud/relay-client.js` 均返回 200，后者引入新发送模块且不再调用旧的 `await this.waitForAck`。
- Cloudflare Worker 生产版本 ID：`029fd809-c087-4060-8b6f-1e8e05df80e4`。

## 待确认的事情

这证明新发送协议在真实生产中继能够完成大于 2 MiB 的字节传输，不等同于证明任意远端浏览器的音频输出已恢复。已有的 Owlbear 页内旧版 JavaScript 不会自动热替换，GM 和接收方需刷新房间再测试。

若刷新后仍有人无声，应区分：

1. 房间歌单与播放状态是否已同步；
2. 接收方本地是否真正已有完整音频（文件大小/哈希及 `owned`）；
3. 如果文件齐全，`HTMLAudioElement.play()` 是否被浏览器自动播放策略拒绝、媒体解码错误、设备音量静音或后台挂起。

朋友使用的浏览器控制台目前不与本机 CDP 连接，不能伪称直接读取过其音频解码异常。必要时让对方复制诊断结果，或为下一版加入按需显式导出的匿名化端侧诊断。
